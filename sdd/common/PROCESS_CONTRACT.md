# SDD 统一过程契约

所有 SDD skill，无论单独调用还是被统一流程编排，都必须遵守本契约。

## 1. 开始前硬约束

1. 读取仓库 `AGENTS.md`、构建/测试入口、已有 design/spec/ADR 和最近变更。
2. 写明本次范围、非范围、基线 commit、目标平台与可用验证环境。
3. 先做只读证据收集；没有用户授权，不连接真实设备、不刷写、不上传、不执行破坏性命令。
4. 用以下证据标签，不得混写：
   - `FACT`：代码、配置、版本库或已执行命令直接证明；必须给出处。
   - `USER_PRIOR`：用户提供的领域先验；记录原意和确认状态。
   - `INFERENCE`：从事实推导；写出推导和反例风险。
   - `UNKNOWN`：当前无法证明；指定负责人或取得证据的方法。
5. 不得伪造命令、测试、评审、用户确认或目标机结果。

## 2. 标识与追踪

使用稳定且仓库内唯一的 ID：`NEED-`、`REQ-`、`IF-`、`CON-`、`RISK-`、`ADR-`、`TEST-`、`EVID-`、`ISSUE-`。删除的 ID 标为 retired，不复用。

规范性需求必须：

- 每条只表达一个行为；使用“系统必须/shall”；
- 指明触发条件、可观察结果和边界；
- 记录来源、优先级、验证方法和验收标准；
- 能追踪为 `NEED → REQ → design element → code → TEST → EVID`。

关键需求任一链路缺失，相关门禁必须 `FAIL`。非规范性说明不得伪装为需求。

## 3. 底层软件必查关注点

逐项判定“适用/不适用并说明理由”：硬件寄存器和 datasheet 版本；ABI/API/协议兼容；字节序、对齐和数据宽度；并发、锁、中断和竞态；时序、超时和实时预算；内存、句柄、带宽和功耗；启动、复位、掉电和错误恢复；升级、回滚和持久化兼容；权限、输入边界和供应链；可观测性与现场诊断；仿真、主机、目标板和硬件在环的证据差异。

## 4. 门禁与判决

统一状态：

- `PASS`：全部阻断项关闭，所需证据真实存在。
- `CONDITIONAL_PASS`：仅剩有负责人、截止条件和隔离措施的非阻断项。
- `FAIL`：验收条件不满足、证据反驳结论或关键追踪缺失。
- `BLOCKED`：必要输入/环境不可获得，无法形成可信判决。

Agent 只输出“建议判决”。人类负责批准 design/spec 基线、风险豁免、架构取舍和流程改进。高风险未知项、未确认的破坏性行为、关键接口不兼容、数据丢失可能性和安全边界缺口不能被条件放行。

## 5. 标准检查点

| Gate | 进入条件 | 退出硬条件 |
|---|---|---|
| G0 Context | 任务和仓库可读 | 范围、权限、命令、平台、陷阱已记录 |
| G1 Inventory | G0 通过 | 模块/接口/依赖/代码范围完整，未知项显式化 |
| G2 Design | G1 通过 | 顶层和受影响模块设计经人检视，关键 ADR 已决 |
| G3 Spec | G2 通过 | 原子需求、验收标准和追踪矩阵建立并获基线确认 |
| G4 Ready | G3 通过 | 变更计划、回滚、测试和资源预算足以实施 |
| G5 Verified | 实现完成 | 静态/单元/集成/目标证据按计划完成，无虚假替代 |
| G6 Deliver | G5 通过 | 文档一致、变更可审计、已知限制和操作风险完整 |
| G7 Improve | 交付或中止后 | 复盘提案已评审；只有确认项写回流程 |

不得跳过 Gate；可以合并执行，但报告中必须逐个给状态和证据。

## 6. 变更与文档一致性

实现时维护“候选文档差异”，验证后再回写事实。改变公共行为、接口、默认值、错误语义、资源上限或安全边界时，必须同时检查顶层设计、模块设计、spec、示例、操作文档、测试说明和 `AGENTS.md`。批准文档只通过变更记录修改，并保留旧结论被替代的原因。

## 7. 结束报告

必须包含：建议判决、变更范围、需求覆盖率、执行过的命令与结果、未执行项、目标机证据、剩余风险、文档差异、需要人确认的决策。没有证据的“完成”“通过”“安全”“兼容”属于流程违规。
